## What changed

`parse_response` previously accepted cached and separately billed cache-write
tokens when each individually fit the input total, even if their sum exceeded
it. It now rejects that joint overflow with `responses_usage_invalid` before
returning an answer/accounting. Zero components, a positive ordinary remainder
and exact equality remain valid. Existing exact integer, nonnegative, component,
total and ceiling checks remain. Usage is neither clamped nor normalized; no
field is dropped and no monetary value or live authorization is introduced.

This implements the partition semantics in the
[official accounting example](https://developers.openai.com/cookbook/articles/per_run_spending_controller_responses_api):
ordinary input is total input minus cached and separately billed cache-write
tokens, and cannot be negative. Only recorded token usage is validated here.

The existing controller/transport already leave rejected attempts durably
reserved without accepted completion. New fake-HTTP regressions verify that
behavior on each response. A valid first response and its retained search/get
remain truthful when the second fails. No candidate acceptance, further send,
refund, retry or replay follows. Runtime activation stays disabled.
